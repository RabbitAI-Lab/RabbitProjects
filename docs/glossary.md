## 一、架构与工程术语

**工作空间（Workspace）**
系统最顶层的组织单元，对应一个团队或一家企业。所有团队、项目、任务、文件、成员、字段配置、工作流均归属且仅归属于一个工作空间，是数据隔离的最外层边界。标准版一个实例通常只有一个工作空间；企业版支持多工作空间隔离与集团—子团队层级治理。URL 与 API 路径均以工作空间 slug 作为一级作用域。

**统一工作项（Unified Work Item / Issue）**
系统的核心数据实体，也是本项目最重要的架构决策：**不单独建设独立的「需求模块」**，需求、缺陷、开发任务、测试项、文档工作全部由同一张工作项表承载，通过「任务类型」字段区分性质。系统内部统一称「任务 / Issue」。该设计避免多套数据模型带来的重复开发与数据割裂，使看板、甘特图、筛选器、工作流、报表、权限体系全部复用同一套底层能力，并让「需求 → 拆解任务 → 开发 → 测试 → 缺陷 → 交付」全链路天然打通、无需跨模块同步。

**任务类型（Issue Type）**
区分工作项性质的分类字段，系统内置**需求 / 缺陷 / 任务 / 测试 / 文档**五种默认类型，团队管理员可自定义新增、改名、停用。每种类型可独立配置专属字段模板、默认状态集、独立工作流、图标颜色与必填规则；例如「需求」类型可配置需求来源、业务价值、验收标准，「缺陷」类型可配置严重等级、复现步骤、影响版本，彼此互不干扰。新建工作项时把类型选为「需求」即完成需求录入。

**动态自定义字段（Dynamic Custom Fields）**
可在管理后台可视化热插拔的任务字段能力：新增、编辑、停用、删除、拖拽排序字段**无需修改数据库表结构、无需执行 DDL、无需版本发版**，配置后立即在新建弹窗、任务详情、看板卡片与所有视图生效。标准版（P2）交付单行文本、多行文本、数字、单选、多选、日期、人员单选、人员多选、复选框、URL、金额、自增编号等基础类型；企业版（P3/P4）补齐级联、关联工作项、日期区间、公式计算、附件字段与字段级权限。所有自定义字段自动支持筛选、排序、分组与视图保存。

**JSONB 扩展列（JSONB Extension Column）**
PostgreSQL 的 JSON Binary 列类型，以二进制结构存储 JSON，支持按键取值与索引，读取性能优于文本型 `json`。本系统在工作项主表上设置 `custom_fields` JSONB 列专门承载自定义字段的值：高频内置字段仍存主表独立列以保证查询性能，自定义字段值统一落入该 JSONB 列，从而实现字段增减不改表结构。

**GIN 索引（Generalized Inverted Index，通用倒排索引）**
PostgreSQL 的倒排索引类型，适用于一列包含多个可检索元素的场景（JSONB、数组、全文检索）。本系统对 `custom_fields` JSONB 列建立 GIN 索引，使自定义字段的包含查询与键值筛选具备接近独立列的检索性能，是「灵活性 + 查询性能」兼顾方案的关键一环。

**RBAC（Role-Based Access Control，基于角色的访问控制）**
权限不直接授予用户，而是授予角色，用户通过被赋予角色间接获得权限。系统内置系统管理员 / 团队管理员 / 普通成员三类核心角色，权限逐级隔离；企业版进一步支持自定义角色组、部门岗位角色与细粒度资源权限。

**三重权限校验（Triple-Layer Permission Check）**
贯穿全系统的越权防护设计，三层缺一不可：
1. **UI 按钮级** — 前端依据当前用户权限决定按钮、菜单、入口的显示 / 禁用，解决「不该看到的操作不出现」；
2. **API 接口级** — 后端在每个接口入口做二次鉴权，不信任任何前端传入的身份与权限声明，解决「绕过前端直接调接口」；
3. **数据库行级** — 查询层强制注入工作空间 / 团队 / 项目 / 成员范围过滤条件，用户只能查到有权范围内的数据行，解决「越权读取他人数据」。

**Monorepo（单仓多包）**
用一个 Git 仓库管理多个相互关联的应用与共享包的工程结构。本项目采用 pnpm workspace + Turborepo：`apps/` 承载 web 主工作台、admin 实例管理后台、space 对外公开空间、api、live、proxy 等应用，`packages/` 承载 UI 组件库、编辑器、类型定义、工具函数等共享包；Turborepo 负责任务编排与增量构建缓存，仓库结构与 Plane 保持一致。

**MobX Store**
前端响应式状态管理单元。以可观察（observable）状态 + 动作（action）+ 计算值（computed）组织领域数据，状态变更自动触发依赖组件重渲染。本系统按领域拆分 Store（如工作空间、项目、工作项、看板视图、通知等），配合 SWR 做服务端数据同步与乐观更新。

**SWR（Stale-While-Revalidate）**
一种数据获取策略：请求先立即返回本地缓存中的「陈旧」数据让界面秒开，同时在后台重新向服务端验证并拉取最新数据，返回后静默更新界面。本系统用 SWR + Axios 承担全部数据请求，配合 MobX 乐观更新与版本号冲突解决，保证多人协作场景下不发生数据覆盖。

**Hocuspocus**
基于 Yjs 的开源实时协作服务端框架（Node.js）。本系统在独立的 live 服务中运行 Hocuspocus，按项目 / 实体隔离 WebSocket 房间，驱动富文本描述与协作文档的多人同时编辑、在线状态与光标同步、持久化与断线重连。

**CRDT（Conflict-free Replicated Data Type，无冲突复制数据类型）**
一类特殊的数据结构，多个副本各自独立并发修改后，无论操作到达顺序如何，合并结果必然一致且无需中心化加锁或人工解冲突。本系统使用 Yjs 这一 CRDT 实现承载协同编辑，因此多人同时编辑同一段文本不会互相覆盖。

**Pragmatic Drag and Drop**
Atlassian 出品的拖拽库（`@atlaskit/pragmatic-drag-and-drop`），基于浏览器原生 HTML5 拖放 API 的轻量封装，性能好、包体积小、可访问性佳，是 Jira / Trello 同源方案。本系统用它实现看板卡片跨列拖拽与同列排序、甘特图任务条拖拽、字段配置拖拽排序。

**DRF（Django REST Framework）**
Django 生态最主流的 RESTful API 框架，提供序列化器、视图集、路由、认证鉴权、分页、过滤与限流等完整能力。本系统全部 API 基于 DRF 构建，并统一封装返回格式与全局异常捕获。

**Celery**
Python 生态的分布式异步任务队列。以 worker 进程消费任务、beat 进程调度定时任务，本系统以 RabbitMQ 作为消息中间件，把邮件通知、文件后处理、报表聚合、自动化规则触发、审批超时提醒等耗时或定时操作移出请求链路，保证接口响应速度与执行可靠性。

**Advisory Lock（咨询锁 / 应用级锁）**
PostgreSQL 提供的应用层显式锁：由应用自行约定锁的键值语义，数据库只负责保证同一键在同一时刻仅被一个会话持有，不与具体表行绑定。本系统在看板拖拽排序、任务依赖变更、工作流状态流转等并发敏感操作中，结合 `transaction.atomic` 事务使用咨询锁，避免并发请求造成排序错乱或状态覆盖。

## 二、业务术语

**标准版（Standard Edition）**
覆盖 P0-P2 全部功能的版本，面向个人用户与中小团队，能力对标 Plane 免费版，覆盖约 80% 通用项目管理场景。包含账号权限基础三级角色、团队与项目管理、完整任务体系、动态自定义字段与全字段筛选器、多看板、甘特图、项目文件库、评论通知与实时同步、GitHub 基础集成、基础统计。第 8 周（Sprint 6）发布 V1.0。

**企业版（Enterprise Edition）**
在标准版之上叠加 P3-P4 功能的版本，面向中大型企业，核心卖点是可视化自定义工作流与审批体系，另含组织架构、自定义角色、细粒度权限、SSO、审计日志、项目集、敏捷报表、Wiki 知识库，以及远期的 LDAP/SCIM、AI 辅助、开放平台、文件合规、私有化部署与数据大屏。第 12 周（Sprint 9）交付 V1.0 核心能力。

**POC（Proof of Concept，概念验证）**
P0 阶段交付物，目标是用最小可用闭环验证全栈技术架构可行性并清零技术风险，而非交付完整产品。范围严格界定为：技术底座跑通、邮箱注册登录、默认团队初始化、项目 CRUD、任务 5 个固定字段 CRUD、固定三列看板拖拽、最小权限隔离。企业版功能、甘特图、文件库、实时同步、评论通知、第三方集成、动态字段等一律后置，坚决避免需求扩散导致延期。验收标准为 5 分钟内完整演示全流程且 `docker compose up` 一键启动。

**MVP（Minimum Viable Product，最小可用产品）**
P1 阶段交付物，在 POC 验证通过后的第一个迭代补齐，目标是让 10 人以内小团队能真实用于日常协作：成员邀请与角色分配、任务优先级 / 截止时间 / 类型 / 标签 / 一级子任务、列表筛选搜索排序、任务附件、评论 @提醒与通知中心、个人任务统计。

**Sprint（敏捷迭代周期）**
固定时长的开发迭代单元。本项目 Sprint 0 为 2 周（POC），Sprint 1-6 各 1 周，Sprint 7 为 2 周，Sprint 8-9 各 1 周。每个 Sprint 结束必须输出可直接操作演示的完整版本，不接受「后端完成、前端未开发」的半成品；上一迭代验收不通过不进入下一迭代。每个 Sprint 固定预留 20% 缓冲时间。

**看板（Kanban Board）**
以列（Column）表示状态、以卡片（Card）表示工作项的可视化任务流转面板。卡片跨列拖拽自动变更任务状态，同列拖拽可自定义排序顺序。POC 阶段为固定三列（待办 / 进行中 / 已完成）；标准版支持列自增删改排序、多个独立看板、筛选与视图配置保存；企业版支持视图团队共享、管理员视图锁定与多维度分组。

**甘特图（Gantt Chart）**
以横向时间轴 + 任务条呈现项目进度的图表。支持日 / 周 / 月时间粒度切换、拖拽任务条修改开始结束时间与工期、任务依赖连线、进度百分比更新、延期高亮与 PNG 导出；企业版补齐关键路径自动计算、延期自动预警、批量进度调整与跨项目甘特汇总。

**工作流（Workflow）**
任务状态流转规则的定义，本质是一台状态机：由状态节点、流转边（Transition）、流转条件、操作权限与触发动作构成。标准版为固定状态流程；企业版支持可视化画布编辑、按任务类型 / 团队配置独立工作流、流转权限管控、流转条件拦截（前置任务未完成禁止流转、字段非空校验、工时必填校验等）与字段锁定。

**审批流（Approval Flow）**
企业级审批链路，作为工作流中的审批网关节点存在。支持单人审批、多人会签（全部同意才通过）、或签（任一同意即通过）、逐级审批、驳回与撤回、审批节点角色绑定、审批超时提醒，并对审批日志、审批意见、操作人与时间节点全量留痕以满足合规审计。

**自动化规则（Automation Rules）**
「事件触发 → 条件判断 → 执行动作」的规则引擎。触发条件如状态变更、任务创建、截止时间临近、字段值变化；执行动作如自动赋值字段、自动指派负责人、自动变更状态、自动发送通知、自动创建关联任务。定时类触发由 Celery beat 承担，动作执行走 Celery worker 异步可靠执行。

**需求池（Requirement Pool）**
内置的专项视图，默认自动筛选「任务类型 = 需求」的全部工作项，作为独立的需求管理入口。支持需求评审、需求排期、需求版本规划、需求统计，以及「需求一键转任务」——把一条需求拆解为多个开发子任务并自动保留父子关联，实现需求到落地的全链路追溯。企业版可为需求类型单独配置独立评审工作流，形成需求评审 / 驳回 / 定稿闭环。

## 四、优先级分级速查

| 级别 | 名称 | 定位 | 交付窗口 |
