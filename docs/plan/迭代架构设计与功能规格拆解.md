# 迭代层级架构设计与功能规格文档拆解计划

## 一、总体方法论

### 执行原则
- **严格按优先级顺序推进**：P0 全部完成并审核通过 → P1 → P2 → P3 → P4，禁止跨阶段并行
- **架构文档先行**：7 份跨迭代架构决策文档作为所有功能规格的基石，最先完成
- **每份文档自包含**：包含业务逻辑、UI/UX、前后端技术架构、测试用例、竞品对标五大模块
- **竞品对标贯穿**：每个功能点必须对比 Plane 开源实现与 Ones 企业方案，阐明本系统的设计选型理由与差异化价值

### 文档规模
| 类别 | 文档数 | 预估页数 |
|------|--------|---------|
| 架构文档 | 7 | 60-80 |
| Sprint 0 (P0) | 10 | 120-150 |
| Sprint 1 (P1) | 11 | 100-130 |
| Sprint 2-6 (P2) | 26 | 380-470 |
| Sprint 7-9 (P3) | 18 | 290-360 |
| P4 远期 | 10 | 100-120 |
| **合计** | **82** | **~1,100** |

## 三、规格文档统一模板

每份功能规格文档严格遵循以下 7 大章节结构：

### 第1章：概述
- 功能定位与价值描述
- 目标用户角色
- 前置依赖表（依赖文档ID / 功能名 / 依赖类型 / 说明）
- 竞品参考表（Plane实现方式 / Ones实现方式 / 本系统设计优势 / 参考链接）

### 第2章：业务逻辑
- 用户流程（Mermaid flowchart）
- 状态机（Mermaid stateDiagram，含触发条件与权限要求）
- 业务规则表（规则编号 / 描述 / 触发条件 / 处理逻辑）
- 异常处理表（异常场景 / 触发条件 / 前端表现 / 后端处理 / 错误码）
- 边界条件表（边界场景 / 限制值 / 超出处理方式）

### 第3章：UI/UX 设计
- 页面布局描述（区域划分、组件层级、使用的 UI 组件）
- 交互细节表（交互动作 / 触发方式 / 反馈效果 / 加载态/空态处理）
- 响应式适配表（断点 / 布局变化 / 功能差异）
- 无障碍要求（键盘导航、ARIA 标签、焦点管理）

### 第4章：技术架构
- 数据模型（Django ORM Model 定义 + Mermaid erDiagram）
- API 定义（方法/路径/描述/权限 + 每个端点的 Request/Response JSON 示例）
- 核心算法与复杂逻辑（伪代码、并发策略、Celery 任务定义）
- 前端状态管理（MobX Store 设计、SWR 缓存策略）
- 实时同步（WebSocket 事件定义，如适用）

### 第5章：测试用例
- 单元测试（用例ID / 测试目标 / 输入 / 预期输出 / 覆盖类型）
- 集成测试（用例ID / 场景 / 前置条件 / 操作步骤 / 预期结果）
- E2E 测试（用例ID / 用户场景 / 操作路径 / 验收标准）
- 边界与异常用例

### 第6章：竞品深度对标
- Plane 实现分析（架构方案、代码路径、设计模式、优劣势）
- Ones 实现分析（功能范围、企业能力、UI/UX 方案、优劣势）
- 本系统设计决策（技术选型理由、架构优势、使用的设计模式、差异化价值）

### 第7章：里程碑与验收
- 交付物清单（Model/Migration、API 端点、前端页面/组件、测试）
- 可操作演示的验收标准

## 四、竞品对标分析框架

### Plane 对标维度（基于开源代码实证）
- **数据模型**：PostgreSQL advisory lock 序列号生成、三格式描述存储(JSON/HTML/Yjs Binary)、Issue 自引用外键子任务
- **权限体系**：双层 RBAC（Workspace 4角色 + Project 4角色）、Owner/Admin 绕过项目成员检查、Custom Roles (EE)
- **前端架构**：MobX observable Store + SWR stale-while-revalidate、Pragmatic DnD 看板拖拽、TipTap 编辑器 + slash commands
- **实时协作**：Hocuspocus Server 单例 + Redis Extension 横向扩展、零停机文档格式迁移（HTML→Yjs Binary）
- **后端架构**：DRF ViewSet + 游标分页 + 字段选择/关联展开、30+ Celery 后台任务、RabbitMQ 消息队列
- **设计模式**：Observer(MobX)、Store、Singleton、Strategy(文档服务)、Command(slash commands)、Event Sourcing lite(Activity tracking)

### Ones 对标维度（基于产品分析）
- **统一工作项模型**：Issue Type 系统（全局配置+项目级覆盖）、Custom Link Types 关联、Issue Hierarchy(Business+)
- **自定义字段**：原生计算字段/级联字段(Business+)、字段级权限、Custom Issue Detail Layout、字段联动规则
- **工作流与审批**：状态机模型(Status+Transition)、Issue Approval(Enterprise)、字段锁定、Approval Center
- **双层自动化**：No-Code 自动化(Standard+) + ONEScript 代码层(JS/TS/Groovy)、Dry Run Sandbox、版本历史
- **企业安全**：SOC 2 + ISO 27001 + CMMI 5、4种部署模式(含气隙)、审计日志、水印系统
- **报表体系**：燃尽图/速度图/累积流图、多指标双轴图、Dashboard 模板与权限

### 差异化价值主张（每份文档须阐明）
1. **技术栈一致性**：与 Plane 完全一致的技术栈，降低学习曲线和迁移成本
2. **统一工作项 + JSONB 动态字段**：参考 Ones 的 Issue Type 系统，但用 PostgreSQL JSONB + GIN 索引实现更灵活的动态字段，无需 DDL 改表
3. **三重权限防护**：综合 Plane 双层 RBAC 与 Ones 字段级权限的优势，实现 UI/API/DB 行级三层校验
4. **渐进式架构**：P0 最小闭环 → P4 企业级，每个阶段独立可用，参考 Plane 的渐进增强模式

## 六、质量控制

### 每份文档的验收标准
1. 业务逻辑完整且无歧义，Mermaid 流程图可渲染
2. API 定义包含完整的 Request/Response JSON 示例
3. 数据模型定义包含字段类型、索引、约束、ER 关系图
4. 测试用例覆盖正常路径、异常路径、边界条件
5. 竞品对标包含 Plane 和 Ones 的具体实现分析（非泛泛而谈）
6. 输出格式统一，可直接指导代码开发

### 风险缓解
| 风险 | 缓解措施 |
|------|---------|
| Sprint 7 工作流复杂度失控 | WF-001/WF-002 拆为画布编辑器和执行引擎两个独立文档 |
| JSONB 字段 P0 预留不足 | INFRA-003 和 TASK-001 中明确预留 customFields JSONB 列 + GIN 索引 |
| 甘特图前端性能 | GANTT-001 须包含虚拟滚动方案和性能基准要求 |
| POC 范围蔓延 | Sprint 0 文档严格对照需求文档 8.3 节 POC 界定，超出内容标注"后置" |
| 标准版/企业版边界模糊 | 每份文档头部标注版本归属，glossary.md 明确功能版本边界 |

## 七、立即执行事项

确认计划后，从架构文档开始，按以下批次执行：

**批次 1**：生成 `docs/README.md` + `docs/glossary.md` + 7 份架构文档
**批次 2**：生成 `sprint-0-poc/sprint-overview.md` + 10 份 Sprint 0 功能规格文档
**批次 3**：提交 Sprint 0 全套文档供用户审核

每批次内多份文档可并行生成（无相互依赖的文档），但批次间严格串行。
